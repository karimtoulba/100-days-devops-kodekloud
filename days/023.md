# Day 023 - Fork a Git Repository (Gitea, Fork)

**100 Days of DevOps, Day 23:** how to fork a repository through the Gitea web UI, giving a developer their own independent copy of an existing project to work from.

## 🎯 Objective

A new developer, Jon, has joined the Nautilus team and needs his own copy of an existing project. Fork the repository using the Gitea web interface.

---

## Why This Matters

Forking is the standard way to give a contributor their own copy of a repository without granting them direct write access to the original — they push changes to their fork and open a pull/merge request back, keeping the source repository's history clean and controlled. This workflow is identical across self-hosted Git services like Gitea and Gitea-based platforms, as well as GitHub and GitLab, which makes it one of the most transferable Git collaboration skills a team member can learn.

---

## Access the Gitea UI

Click the **Gitea UI** button on the top bar of the lab environment.

This opens the Gitea web interface, the self-hosted Git service used for this lab environment's repositories.

---

## Log In to Gitea

```
Username: jon
Password: Jon_pass123
```

Authenticates as Jon, the new developer, so the fork is created under his own account/namespace.

---

## Locate the Repository

Navigate to the repository owned by `sarah`:

```
sarah/story-blog
```

Identifies the source repository that needs to be forked, owned by team member `sarah`.

---

## Fork the Repository

1. Open the `sarah/story-blog` repository page.
2. Click the **Fork** button in the top-right corner.
3. Select **jon** as the destination namespace/owner.
4. Confirm the fork.

The Fork action creates a full, independent copy of `sarah/story-blog` under Jon's own namespace, complete with its own commit history, that Jon can push to freely.

---

## Verify the Fork

Navigate to Jon's namespace and confirm the forked repository exists:

```
jon/story-blog
```

Confirms the fork completed successfully and Jon now has his own copy of the project to work from.

---

## Key Takeaways

- Forking creates an independent, full copy of a repository under a different owner — no write access to the original is needed.
- The forked repo retains the original's full commit history at the time of the fork.
- This is the standard onboarding pattern for adding a new contributor without exposing the source repository to direct pushes.
- The same fork-and-pull-request workflow applies whether the Git host is Gitea, GitHub, or GitLab.
