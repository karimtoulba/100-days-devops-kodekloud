# Day 017 - Install and Configure PostgreSQL (psql, CREATE USER, GRANT)

**100 Days of DevOps, Day 17:** how to connect to PostgreSQL as the superuser and provision a new application database along with a dedicated, password-protected database user and privileges.

## 🎯 Objective

Install PostgreSQL and create a database user, database, and required privileges.

---

## Why This Matters

Creating a dedicated database user with scoped privileges — instead of letting applications connect as the `postgres` superuser — is a basic but critical database security practice. It limits the blast radius if application credentials leak, makes it possible to audit which app owns which data, and keeps different applications from being able to touch each other's databases on a shared PostgreSQL instance.

---

## Access PostgreSQL

```bash
sudo -u postgres psql
```

Switches to the `postgres` operating-system user and opens the `psql` interactive shell using PostgreSQL's default peer authentication, which is the standard way to get initial administrative access to a local PostgreSQL instance.

---

## Create User and Database

```bash
CREATE USER my_user WITH PASSWORD 'my_secure_password';
CREATE DATABASE my_database OWNER my_user;
GRANT ALL PRIVILEGES ON DATABASE my_database TO my_user;
```

`CREATE USER` provisions a new, password-authenticated database role; `CREATE DATABASE ... OWNER` creates a database and assigns that role as its owner; and `GRANT ALL PRIVILEGES` makes the ownership explicit by granting full rights on the database to that user — the combination an application needs to fully manage its own database without superuser access.

---

## Key Takeaways

- Application databases should be owned by a dedicated, scoped user — never the `postgres` superuser.
- `CREATE DATABASE ... OWNER <user>` and `GRANT ALL PRIVILEGES` together give a user full control of just their own database.
- `sudo -u postgres psql` is the standard entry point for initial administrative access on a freshly installed PostgreSQL server.
- Scoping privileges per database limits the impact of a single set of leaked credentials.
