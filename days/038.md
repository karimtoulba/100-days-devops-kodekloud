# Day 038 - Pull Docker Image and Re-Tag It (docker pull, docker tag)

**100 Days of DevOps, Day 38:** how to pull a specific image tag from Docker Hub and create an additional tag pointing at the same image — useful for preparing a testing environment without duplicating image data.

## 🎯 Objective

On the app server, pull the `busybox:musl` image and re-tag it as `busybox:blog`.

---

## Why This Matters

Re-tagging an image doesn't create a copy — both tags point at the same underlying image ID, so you get a second, more descriptive or environment-specific name for free. This is how teams commonly promote or alias images (`myapp:1.4.2` → `myapp:blog`, or `:latest` → `:staging`) without re-downloading or rebuilding anything.

---

## Connect to the App Server

```bash
ssh steve@stapp02
sudo su -
```

---

## Check Existing Images

```bash
docker images
```

Establishes a baseline before pulling, so it's clear what's new afterward.

---

## Pull the Image

```bash
docker pull busybox:musl
```

Downloads the `musl`-tagged BusyBox image from Docker Hub.

---

## Re-Tag the Image

```bash
docker image tag busybox:musl busybox:blog
```

Creates a new tag, `busybox:blog`, pointing at the same image ID as `busybox:musl` — no new layers are downloaded or created.

---

## Verify the Result

```bash
docker images
```

Both `busybox:musl` and `busybox:blog` should appear in the listing with the **same IMAGE ID**, confirming they reference identical image data.

---

## Key Takeaways

- `docker pull <image>:<tag>` fetches a specific tagged version of an image from a registry.
- `docker image tag <source> <target>` adds a new tag without duplicating the image — both names share the same IMAGE ID and layers.
- Re-tagging is the standard way to alias or promote an image across environments without a rebuild.
- `docker images` showing identical IMAGE IDs for two tags is the tell that they're the same image under different names.
