# Day 026 - Git Manage Remotes (git remote add, git push)

**100 Days of DevOps, Day 26:** how to add a second remote to an existing Git repository with `git remote add` and push a commit to it, a common pattern for mirroring or migrating a repo to a new server.

## 🎯 Objective

Add a new remote to an existing repository, commit a new file to `master`, and push the changes to that remote.

---

## Why This Matters

Real-world repositories often need to sync with more than one remote — a mirror, a backup server, or a migration target. Knowing how to add and manage additional remotes with `git remote add` (rather than just relying on `origin`) is essential when moving a repo between Git servers or setting up redundant backups without losing existing history.

---

## Connect to the Storage Server

```bash
ssh natasha@ststor01
```

This lab's Git repositories live on the storage server, so every task starts by SSHing there.

---

## Navigate to the Repository

```bash
cd /usr/kodekloudrepos/blog
```

Moves into the existing cloned repository so the remote and commit operations run against the right project.

---

## Add the New Remote

```bash
sudo git remote add dev_blog /opt/xfusioncorp_blog.git
```

`git remote add <name> <url>` registers a second remote called `dev_blog`, pointing at a bare repository on disk, without touching the existing `origin` remote.

---

## Verify the Remote

```bash
sudo git remote -v
```

`git remote -v` lists every configured remote and its fetch/push URLs, confirming `dev_blog` was added correctly.

---

## Switch to Master

```bash
sudo git switch master
```

Ensures the new commit is made on the `master` branch rather than whatever branch was previously checked out.

---

## Copy the New File into the Repository

```bash
sudo cp /tmp/index.html .
```

Copies the file to be tracked into the working directory of the repository.

---

## Stage and Commit the File

```bash
sudo git add index.html
sudo git commit -m "Add index.html to master branch"
```

`git add` stages the new file and `git commit` records it in local history on `master`, ready to be pushed.

---

## Push Changes to the New Remote

```bash
sudo git push dev_blog master
```

Pushes the local `master` branch — including the new commit — specifically to the `dev_blog` remote rather than the default `origin`.

---

## Verify the Push

```bash
sudo git log --oneline
```

Confirms the new commit is present in the local history that was just pushed.

---

## Key Takeaways

- A repository can have multiple remotes at once; `origin` is just a convention, not a requirement.
- `git remote add <name> <url>` is how you register an additional push/fetch destination.
- `git push <remote> <branch>` lets you target a specific remote explicitly instead of always pushing to `origin`.
- `git remote -v` is the quickest way to audit which remotes a repo is currently configured with.
