# Day 009 - MariaDB Troubleshooting (systemctl, chown)

**100 Days of DevOps, Day 9:** how to troubleshoot a failed MariaDB service by reading `systemctl status` and log output, tracing the failure to a directory ownership issue, and fixing it with `chown`.

## 🎯 Objective

Troubleshoot a failed MariaDB service and restore it to a running state by diagnosing and fixing an underlying permission issue.

---

## Why This Matters

Service failures caused by ownership or permission mismatches are one of the most common production incidents in Linux systems administration — a runtime directory gets recreated with the wrong owner (often after a reboot or package upgrade) and the service that depends on it can no longer write to it. The workflow here — check status, read the logs, inspect the filesystem, then fix — is the general troubleshooting pattern that applies to almost any failed systemd service, not just MariaDB.

---

## Check Service Status

```bash
sudo systemctl status mariadb
```

`systemctl status` shows whether the service is active, failed, or inactive, along with the most recent log lines — usually the fastest first clue when a service won't start.

---

## Check the Logs

```bash
sudo tail -30 /var/log/mariadb/mariadb.log
```

Reading the last 30 lines of MariaDB's own log file surfaces the specific error the service hit on startup, beyond what `systemctl status` summarizes.

---

## Verify Directory Permissions

```bash
ls -ld /run/mariadb
```

The directory was owned by `root:mysql`, preventing the `mysql` user from writing to it. :contentReference[oaicite:1]{index=1} Since the MariaDB service runs as the `mysql` user, it needs write access to its own runtime directory to create its socket and PID files.

---

## Fix the Ownership

```bash
sudo chown mysql:mysql /run/mariadb
```

`chown mysql:mysql` changes the directory's owner and group to `mysql`, giving the MariaDB service the write access it needs to start.

---

## Restart MariaDB

```bash
sudo systemctl restart mariadb
```

With ownership corrected, restarting the service lets it recreate its runtime files successfully.

---

## Verify the Service

```bash
sudo systemctl status mariadb
```

Expected:

```text
Active: active (running)
```

An `active (running)` status confirms MariaDB started cleanly after the ownership fix.

---

## Key Takeaways

- `systemctl status` and the service's own log file (`/var/log/mariadb/mariadb.log`) together usually pinpoint why a service failed to start.
- Ownership mismatches on runtime directories are a common cause of services failing after a reboot or upgrade.
- `chown user:group <path>` restores the permissions a service account needs to write its runtime files.
- Always verify the fix by restarting the service and re-checking its status, rather than assuming the fix worked.
