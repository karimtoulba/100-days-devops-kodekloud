# Day 027 - Git Revert Some Changes (git revert)

**100 Days of DevOps, Day 27:** how to safely undo a bad commit on a shared branch with `git revert`, which creates a new inverse commit instead of rewriting history.

## 🎯 Objective

The latest commit pushed to the shared repository introduced an issue. Revert `HEAD` to undo it while preserving commit history.

---

## Why This Matters

On a shared branch, rewriting history with `git reset` or force-pushing after removing commits is dangerous — anyone else who has already pulled will get diverged history and broken merges. `git revert` fixes this safely: it adds a new commit that undoes the changes, leaving the original commit (and the record that something went wrong and was fixed) intact. This is the standard, team-safe way to back out a bad change once it has already been pushed.

---

## Connect to the Storage Server

```bash
ssh natasha@ststor01
```

Connects to the server hosting the shared Git repository.

---

## Switch to the Root User

```bash
sudo su
```

Elevates to root so subsequent Git commands can operate on the repository without individual `sudo` prefixes.

---

## Navigate to the Repository

```bash
cd /usr/kodekloudrepos/blog
```

Moves into the repository containing the problematic commit.

---

## Review Commit History

```bash
git log --oneline
```

Lists recent commits so the bad commit at `HEAD` can be identified before reverting it.

---

## Revert the Latest Commit

```bash
git revert HEAD
```

When prompted for a commit message, use:

```
revert blog
```

`git revert HEAD` creates a brand-new commit that applies the exact inverse of the most recent commit's changes, undoing the issue without deleting or rewriting the original commit from history.

---

## Verify the Revert

```bash
git log --oneline
```

Confirms the new revert commit now sits on top of history, with the original problematic commit still visible beneath it.

---

## Push the Revert Commit

```bash
git push origin master
```

Publishes the revert commit to the shared remote so everyone else's `master` branch reflects the fix — with no force-push and no rewritten history required.

---

## Key Takeaways

- `git revert` undoes a commit's changes by adding a new commit, unlike `git reset` which rewrites history.
- Reverting is the safe choice on any branch other people have already pulled from.
- The original "bad" commit stays in history, giving a clear audit trail of what happened and how it was fixed.
- No force-push is needed after a revert — it plays nicely with everyone else's existing clones.
