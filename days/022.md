# Day 022 - Clone Git Repository on Storage Server (git clone)

**100 Days of DevOps, Day 22:** how to clone a local bare Git repository into a working directory so a development team has an actual checkout to edit, commit, and push from.

## 🎯 Objective

Clone an existing bare Git repository into a working directory on the storage server for the development team to use.

---

## Why This Matters

A bare repository (like the one created in Day 021) can't be edited directly — it has no working tree. Cloning it produces a normal, working repository with a checked-out copy of the files plus an `origin` remote already pointing back at the bare repo, which is exactly the setup a development team needs to start committing and pushing changes. This same local-path clone pattern also mirrors cloning over SSH or HTTPS from a hosted Git service — the mechanics are identical.

---

## Connect to the Storage Server

```bash
ssh natasha@ststor01
```

Logs in to the storage server where both the bare repository and the new working clone will live.

---

## Clone the Repository

```bash
sudo git clone /opt/blog.git /usr/kodekloudrepos/blog
```

Clones the bare repository at `/opt/blog.git` into a new working directory at `/usr/kodekloudrepos/blog`, automatically configuring the bare repo as the `origin` remote.

---

## Verify the Clone

```bash
cd /usr/kodekloudrepos/blog
git status
```

Confirms the clone succeeded and shows the working tree is clean and tracking the correct branch.

---

## Key Takeaways

- `git clone` turns a bare repository into a usable working copy, with `origin` pre-configured to point back at the source.
- Cloning from a local filesystem path works identically to cloning over SSH or HTTPS — same command, same resulting remote setup.
- `git status` right after a clone is a quick sanity check that the working tree and branch tracking are correct before making changes.
- This working clone is where the development team will actually edit files, in contrast to the bare repo, which stores history only.
