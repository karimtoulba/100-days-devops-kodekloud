# Day 033 - Resolve Git Merge Conflicts (git pull, conflict markers)

**100 Days of DevOps, Day 33:** how to handle a rejected push, trigger a merge conflict with `git pull`, and manually resolve conflict markers before completing the merge — a routine but essential skill for any team sharing a Git branch.

## 🎯 Objective

Sarah and Max have both been editing the same story file. Push Max's local changes, resolve the resulting merge conflict, and fix a typo in the process.

---

## Why This Matters

Merge conflicts are inevitable the moment more than one person edits the same file — they aren't a sign something went wrong, just Git flagging that it can't automatically decide which change should win. Every developer needs to be comfortable reading conflict markers, understanding both sides of a conflict, and manually reconciling them, because this happens constantly on active shared branches and blocking on it (or resolving it carelessly) stalls the whole team.

```bash
ssh max@ststor01
```


Logs in as `max`, who has local changes to the same file Sarah has already modified upstream.

---

## Navigate to the Repository

```bash
cd ~/story-blog
```

Moves into the repository containing the shared story file both Sarah and Max have been editing.

---

## Attempt to Push Local Changes

```bash
git add .
git commit -m "Update story-index.txt"
git push origin master
```

The push is rejected because Sarah's changes already exist upstream.

Git refuses the push because the remote `master` has commits the local branch doesn't have — Sarah's changes — so Max's branch must be updated before it can push.

---

## Pull and Trigger the Merge

```bash
git pull origin master
```

Git pauses and marks `story-index.txt` as conflicted.

`git pull` fetches Sarah's commit and attempts to merge it with Max's local commit. Since both touched the same lines of `story-index.txt`, Git can't auto-merge and stops, leaving the file marked as conflicted for manual resolution.

---

## Resolve the Conflict

```bash
vim story-index.txt
```

Remove the conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`) and fix the typo:

```
Mooose -> Mouse
```

Opening the file in `vim` shows both versions of the conflicting section side by side, delimited by Git's conflict markers. Resolving means deciding what the final content should be, removing the markers, and — in this case — also fixing an unrelated typo while already in the file.

---

## Stage and Complete the Merge

```bash
git add story-index.txt
git commit -m "Resolve merge conflict in story-index.txt"
```

Staging the resolved file tells Git the conflict is settled, and committing finalizes the merge with both Sarah's and Max's changes combined.

---

## Push the Resolved Changes

```bash
git push origin master
```

With the merge commit in place, the local `master` is now ahead of the remote in a way Git can fast-forward, so the push succeeds.

---

## Verify via Gitea UI

Log in as `sarah` (`Sarah_pass123`) or `max` (`Max_pass123`) and confirm the latest commit and the corrected `story-index.txt` in the `story-blog` repository.

---

## Key Takeaways

- A push gets rejected whenever the remote branch has commits the local branch doesn't have yet — `git pull` first is the fix.
- Conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`) show both sides of a conflicting change; resolving means editing them away to the final intended content.
- Once conflicts are resolved, `git add` + `git commit` completes the merge like any normal commit.
- A conflict is a good opportunity to double-check the surrounding content too — this task also caught and fixed an unrelated typo.
