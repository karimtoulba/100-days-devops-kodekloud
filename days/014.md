# Day 014 - Linux Process Troubleshooting (ss, systemctl, iptables)

**100 Days of DevOps, Day 14:** how to diagnose a service conflict on Linux by inspecting listening processes, correct it by swapping the wrong service for the right one, and open firewall access to match.

## 🎯 Objective

Troubleshoot a service conflict, start the correct service, and allow network access through the firewall.

---

## Why This Matters

"The web server is down" often turns out to be a process conflict — the wrong service is running, holding a port, or simply never started. Being able to quickly answer "what's actually listening on this port, and is it the service I expect?" is one of the most frequently used troubleshooting skills in production Linux support, and it's usually the fastest path from a vague outage report to a concrete root cause.

---

## Check Listening Services

```bash
ss -tulnp
```

Lists every listening TCP/UDP socket with its owning process, giving a full picture of what's actually running and bound to ports on the host.

---

## Check Apache Status

```bash
systemctl status httpd
```

Confirms whether Apache (`httpd`) — the service expected to be serving traffic — is actually running.

---

## Stop and Disable Sendmail

```bash
sudo systemctl disable --now sendmail
```

`disable --now` stops Sendmail immediately and prevents it from starting again on future boots, removing it as a source of conflict.

---

## Start and Enable Apache

```bash
sudo systemctl enable --now httpd
```

Starts Apache right away and enables it to persist across reboots, ensuring the correct web server stays up going forward.

---

## Allow Port 8084

```bash
sudo iptables -A INPUT -p tcp --dport 8084 -j ACCEPT
```

Appends a rule accepting TCP traffic on port `8084`, the port Apache needs to be reachable on.

---

## Save Firewall Rules

```bash
sudo sh -c 'iptables-save > /etc/sysconfig/iptables'
```

Persists the current rule set to disk so it survives a service restart or system reboot.

---

## Restart IPTables

```bash
sudo systemctl restart iptables
```

Reloads the firewall with the saved rules to confirm the persisted configuration matches what's active.

---

## Verify

```bash
systemctl status httpd
ss -tulnp | grep 8084
```

Confirms both that Apache is active and that it — not some other process — is the one listening on port `8084`.

---

## Key Takeaways

- `ss -tulnp` is the fastest way to see exactly which process owns a given port, which is essential when troubleshooting "service won't start" issues.
- A "down" service is often actually a port conflict with an unrelated service that should have been disabled.
- `systemctl disable --now` and `enable --now` combine the immediate action with the persistent boot-time state in a single command.
- Firewall rules and service state should be verified together — a running service on a blocked port is still unreachable.
