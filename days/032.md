# Day 032 - Git Rebase (git rebase, git rebase --continue)

**100 Days of DevOps, Day 32:** how to bring a feature branch up to date with `master` using `git rebase` instead of a merge, keeping a linear commit history and resolving conflicts along the way.

## 🎯 Objective

A developer's `feature` branch is behind `master`. Rebase `feature` onto `master` without losing any work and without creating a merge commit, then push the result.

---

## Why This Matters

Rebasing rewrites a branch's commits to sit on top of another branch's latest state, producing a clean, linear history instead of the extra merge commit a `git merge` would create. This makes `git log` and code review much easier to follow on active feature branches. The trade-off is that rebasing rewrites commit hashes, so it should only be done on branches that haven't been shared with others yet — or with a heads-up and a force push, as done here.

cd /usr/kodekloudrepos/blog

Moves into the repository containing the `feature` and `master` branches.

---

## Configure Git Identity (if needed)

```bash
git config --global user.email "natasha@stratos.xfusioncorp.com"
git config --global user.name "natasha"
```

Sets the Git author identity used for any new commits created during the rebase (such as conflict-resolution commits), which Git requires before it will let you commit.

---

## Update the Master Branch

```bash
git switch master
git pull origin master
```

Ensures the local `master` branch has the latest commits from the remote before `feature` is rebased onto it.

---

## Switch to the Feature Branch

```bash
git switch feature
git pull origin feature
```

Moves to `feature` and syncs it with the remote to make sure no local rebase starts from stale history.

---

## Rebase Feature onto Master

```bash
git rebase master
```

Resolve any conflicts if prompted, then continue:

```bash
git add <resolved-file>
git rebase --continue
```

`git rebase master` replays each commit from `feature` one at a time on top of the latest `master`, instead of creating a single merge commit. If a commit's changes conflict with `master`, Git pauses so the conflict can be resolved manually; staging the resolved file and running `git rebase --continue` resumes replaying the remaining commits.

---

## Push the Rebased Branch

```bash
git push origin feature --force
```

Because rebasing rewrites commit hashes, the local `feature` branch no longer matches the remote's history, so a force push is required to update it.

---

## Verify the History

```bash
git log --oneline
```

Confirms `feature`'s commits now sit cleanly on top of `master`'s latest commit, with no merge commit in the log.

---

## Key Takeaways

- `git rebase` replays commits onto a new base, producing linear history instead of the extra merge commit `git merge` creates.
- Conflicts during a rebase are resolved one commit at a time via `git add` + `git rebase --continue`.
- Rebasing rewrites commit hashes, so a force push is required afterward — and it should only be done on branches not yet relied upon by others.
- Keeping both `master` and `feature` up to date with `git pull` before rebasing avoids rebasing against stale history.
